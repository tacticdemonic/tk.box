## 1. Confirmed cost — the original diagnosis was partly wrong

The report attributed the 54 s page to repeated guide decryption. **Guide decryption was not the
cost.** Counting real vault operations during one 50-row page at `1d2c3c7` showed:

| Operation | Count per 50-row page | Verdict |
| --- | --- | --- |
| Guide blob decryption (`iptv:guide:*`) | 1 | already request-scoped, as M03.4 claimed |
| Guide JSON parse | 1 | same |
| **`iptv_sources` metadata read** | **192** | **dominant** |
| Per-channel metadata decryption + parse | ~8,400 (feeds and stacks pass) | second cost |
| Programme array scans (`guideWindow`) | 50 (one per row) | third cost |

### 1.1 The dominant defect: `IS NOT NULL` walks the whole guide blob

`IptvStore.source()` projected `encrypted_guide IS NOT NULL AS has_guide`. SQLite evaluates
`IS NOT NULL` on a stored value by reading it: on the real 37,611,340-byte guide that means walking
the entire overflow-page chain. Measured on the reproduction dataset, per call:

| Projection | ms/call |
| --- | --- |
| `SELECT id` | 0.010 |
| `SELECT id,name,revision` | 0.009 |
| `+ encrypted_endpoint` | 0.012 |
| `+ encrypted_snapshot IS NOT NULL` | 0.975 |
| **`+ encrypted_guide IS NOT NULL`** | **20.844** |
| `+ length(encrypted_guide)` | 59.932 |
| **`+ typeof(encrypted_guide)`** | **0.010** |

The guide page calls `source()` once per feed through `feedFor()` → `guideSource()` → `source()`.
At 8,436 feeds that is hundreds of full-blob walks per page — which is why the page took seconds
while `/health` (no guide read) stayed at 3 ms. The fix is `typeof(encrypted_guide)='text'`, which
reads only the value's header. Same semantics, 20.8 ms → 0.01 ms.

This is the measurement that explains the reported 54,428 ms page. Everything else below is real
but secondary.

### 1.2 Duplicate programme data

`sourceData()` parsed the sealed **catalogue** for an Xtream source to obtain channel metadata.
That catalogue carries its own full copy of the guide, so every cold read parsed the programme
collection twice: once from `xtream_accounts.encrypted_catalogue`, once from
`iptv_sources.encrypted_guide`. The published snapshot (`iptv_sources.encrypted_snapshot`) is the
small authoritative channel list and is now the only source of channel metadata.

### 1.3 Per-channel metadata, decrypting once per channel per request

Channel metadata is sealed per row. `provider()` decrypted and parsed it on every call, and a
lineup pass calls it once per channel. It is now cached by its own sealed payload: a replaced feed
is a new key, so the cache cannot serve stale metadata, and it needs no invalidation bookkeeping.

### 1.4 Per-row full-guide scans

`guideWindow()` filtered and sorted the entire programme collection for every displayed row: 50
rows × 62,660 programmes. Programmes are now grouped by guide id once per guide snapshot, and a
window is one binary search plus the programmes actually on screen.

### 1.5 Station index rebuilt on every miss

`usableGuideId()` fell back to `guideStations(xml.channels)` whenever an indexed lookup returned
`undefined`. With a complete index a missing id is a legitimate miss, so the fallback rebuilt the
station map for every channel whose id was absent — turning the common missing-id case into
quadratic work. The fallback now applies only when no index was supplied.

### 1.6 Minute boundary

`automaticStackKeys()` keyed its cache on `JSON.stringify([..., now, mappings])`, so the whole
mapping resolution and guide regrouping repeated at every clock minute. Only the schedule
comparison depends on the clock: the resolved candidates and their programmes are immutable for a
revision. The minute now re-joins cached evidence; a revision or mapping change invalidates it.

## 4. Review fixes (M03.5 follow-up)

Four findings were reproduced before they were repaired. Each has a failing-first regression in the
suite that now passes.

### 4.1 Linked M3U/XMLTV cache invalidation

**Reproduced.** With one `IptvStore`, publishing an M3U playlist linked to an XMLTV guide, warming
guide/mapping/stack/logo reads and then refreshing only the guide left the playlist's cached
`SourceData` — and the `GuideIndex` inside it — at the previous guide revision. The logo kept the
old icon and a newly declared guide id never resolved. `tests/linked-guide-invalidation.test.ts`
failed on exactly that assertion at the reviewed HEAD.

**Corrected design.** `dataKey()` for an M3U source now names the linked feed and that feed's
revision as well as the playlist's own revision. A guide-only refresh therefore produces a new key,
and the old entry is evicted by the existing per-source rule. Nothing is cleared globally: an
Xtream or XMLTV source, or an unlinked playlist, keeps its key and its cache hit. The key costs two
small indexed queries on a miss only.

**Regression coverage.** One guide refresh now updates the icon, resolves a previously absent id,
turns an id that names two stations ambiguous, and a later refresh resolves it again. Two playlists
sharing one guide both see the update; relinking one playlist to another guide replaces its icon and
mapping and leaves the first playlist untouched. All on one store instance, with no playlist
refresh, cache-clear or restart.

### 4.2 The derived icon projection

**Reproduced.** `coverage()` wrote the raw guide `<icon src>` value into `iptv_channel_icons`. A
provider URL may carry an access token, so an encrypted guide leaked it into plaintext storage.
`tests/logo-projection.test.ts` asserts the token is absent from every persisted column.

**Corrected design.** The projection still stores one small row per channel so a logo request never
decrypts or parses the guide. The URL is now sealed with the channel as its context
(`iptv:icon:<channelId>`) and prefixed with `sealed:`, so:

- a logo request performs one small authenticated decryption, never a guide read;
- a row copied onto another channel fails authentication and is treated as absent;
- an unsealed value — a pre-1006 row or a restored backup — is ignored rather than served;
- the raw URL reaches only the authorised server-side image fetch, never a row, response or log;
- SSRF, redirect, size and TLS controls in `ChannelLogos` are untouched;
- authorisation still runs before the projection is read, including on a warm row.

**Migration.** Migration 1006 deletes rows that do not carry the `sealed:` marker. A development
database that already applied 1005 drops its plaintext rows on the next startup and the existing
`relistAll()` republishes them sealed from the guide already stored. No reimport is required.
Deleting the live rows does not rewrite historical WAL pages, backups or copies already taken, and
this record makes no such claim.

### 4.3 Cache accounting and ownership

**Reproduced and corrected.** Reviewing the retained-object graph, not just `dataCache.size`:

| Defect | Correction |
| --- | --- |
| The entry-count reset called `dataCache.clear()` without zeroing `dataCacheBytes`, so every later eviction removed the wrong entries. | `clearDataCache()` clears entries, the counter and the schedule cache together. |
| A single entry larger than the budget was evicted immediately and re-read on the next request, thrashing forever. | Explicit policy: the oversized entry is kept alone; the request completes and the next miss replaces it. Its weight is reported honestly above the budget. |
| `scheduleStackCache` candidates kept programme arrays from superseded guides alive after their data-cache entry was gone, and could serve them under a stale key. | Each entry records the data-cache keys it borrowed; eviction or replacement of either source drops the schedule entry. Removing a source drops its entries immediately. |
| The budget was described as memory. | It is documented as **estimated sealed-payload bytes**; tests and the benchmark report logical weight separately from RSS. |

A `dataCacheBytes` constructor seam lets the tests use small budgets instead of allocating hundreds
of megabytes. `cacheStats()` exposes the logical weight for tests and the benchmark only.

**Tests** (`tests/cache-accounting.test.ts`, 5): eviction at the budget with correct results after
rebuild; a single oversized entry; several sources near the budget; source removal and replacement;
clearing and reusing the cache; repeated refreshes with programme retention.

### 4.4 Logo rate-limit override

Retained at 1,200/minute; the exact policy and its separation from the 120/minute default is
tabulated in §8. `tests/logo-rate-limit.test.ts` (6) covers a normal 50–60-logo burst that leaves
`/health` and `/api/v1/me` usable, per-client sharing across channel ids, rejection after 1,200
requests, unauthenticated rejection, a mutation route that keeps the default policy, and a forged
`X-Forwarded-For` that cannot change the limiter key. No real provider is contacted: a login attempt
uses a local transport double that fails immediately.

## 9. One deliberate limit change

The logo route had no limit of its own, so a guide page's 50–60 logo requests drew on the shared
120/min ceiling. On a real device that means ordinary browsing can exhaust the budget that `/health`,
`/api/v1/me` and every other route share, and a benchmark burst produced `429 RATE_LIMITED` on
`/health`. The logo route now carries its own 1,200/min ceiling, exactly as the live-segment and HLS
routes already do for the same reason.

Precisely, the policy is:

| Route class | Allowance | Scope of the counter |
| --- | --- | --- |
| `GET /api/v1/iptv/channels/:id/logo` | **1,200 requests / 60 s** | one counter per client address, shared by every logo request of every channel |
| Every other route without its own override (`/health`, `/api/v1/me`, the guide, catalogue reads) | **120 requests / 60 s** | one counter per client address, shared across those routes |
| Sign-in (`/api/v1/auth/xtream/login`, `/api/v1/auth/plex/start`) | 10 / 60 s | route-specific override |
| Live playback session create / VOD session create | 30 / 60 s and 20 / 60 s | route-specific override |
| Live segments and HLS paths | 1,200 / 60 s | route-specific override |

These are separate limiter stores keyed by the same client address, so a logo burst does not spend
the control-route budget and exhausting the control-route budget does not block logos. **There is no
second, aggregate 120/min ceiling over logo traffic**: the only limit on the logo route is its own
1,200/min allowance. `tests/logo-rate-limit.test.ts` asserts exactly that, including that 1,201
requests are rejected and that `/health` and `/api/v1/me` still answer afterwards.

The limiter keys on the client address; `X-Forwarded-For` is only trusted when `TRUSTED_PROXY_CIDRS`
makes Fastify trust the peer, so an untrusted header cannot mint a fresh allowance.

## 11. Remaining unknowns

- The single-logo p95 of 1,623 ms here is dominated by the first external fetch in a burst and the
  logo-library index load, both bounded and cached. Real-provider fetch latency (the reported
  0.88–0.90 s) cannot be reproduced without that provider, so the physical run is what confirms it.
- The synthetic guide is representative in size and shape, not in provider-specific quirks: it does
  not reproduce the exact 8,385-channel/69,733-programme feed M03.4 imported. The counts and the
  shape of the defect are what carry over.
- The data cache budget (96 MiB of **estimated sealed-payload bytes**) is sized for two full guides
  plus their channel snapshots. It is a logical weight, not a heap or RSS measurement: the
  decrypted objects may occupy a different amount. A deployment with many large providers at once
  will evict and re-read rather than grow without bound; that is the intended trade-off, not a
  measured limit.

### 12.1 Reproduction, and what the delay actually was

The server was never slow here. A real Chromium drove the compiled server through a proxy that holds
every `/logo` response for a controlled delay, which keeps the browser's real connection pool in the
path — a mocked `fetch` would have bypassed exactly the mechanism at fault. Dataset and publication
path as in §5.

The measurement that separates the phases is the browser's own resource timing for the guide
request, which splits queueing from server work. **Each phase below has a defined start and end**
(the first revision of this table put the click-to-usable total in a row labelled response-to-render,
which double-counted every earlier phase):

| Phase | Start → end | How it is taken |
| --- | --- | --- |
| Click → dispatch | the click handler runs → the guide request's `startTime` | `resource.startTime - click` |
| Queueing | request created → `requestStart` | `requestStart - startTime`; includes browser connection acquisition |
| Request/response | `requestStart` → `responseStart` | server work plus transfer of the headers |
| Body transfer | `responseStart` → `responseEnd` | guide JSON download |
| Response → render | `responseEnd` → the frame after React commits the rows | `requestAnimationFrame` after the rows appear |
| Click → usable | click → that same painted frame | the sum of the phases above |

| Phase | Before the fix (`73d640c`, no cap) | After the fix |
| --- | --- | --- |
| Click → dispatch | 3–16 ms | 4–10 ms |
| **In the browser's connection queue** | **6,215 ms** | **1 ms** |
| Request → response (server work) | 448 ms | 210–331 ms |
| Response → render | not measured separately | 51–101 ms |
| **Click → usable** | **~6.7 s** (16 + 6,215 + 448 + render) | **272–316 ms** |
| Logo completion | still pending | still pending |

The 6,215 ms was measured on the pre-cap build with logo responses held. Re-measured on this
candidate with the same proxy holding logos, queueing is **1 ms** in every transition and
click-to-usable is **272–316 ms** over three transitions (a fourth run measured 276–406 ms; both
sets are the same build). On the pre-cap build the same click
produced **zero rendered rows** within 30 s while six logo connections were held: the guide request
never left the queue, which is the defect stated as a measurement rather than a latency figure.

**Cause.** `ChannelLogo` rendered `<img loading="lazy">`. Lazy loading is a *hint*, and the Fire TV
WebView (Chromium ~66 per `apps/web/src/compat.ts`) does not implement it, so every logo on the page
started immediately — 50 requests. A page is allowed about six connections per origin, so the 50
logo fetches occupied all of them, and the next guide request waited in that queue. It was not the
guide handler awaiting images, and not server work: the same request the browser finally dispatched
answered in 448 ms.

This is a browser-scheduling defect, so the measurement has to be the browser's. `tests/guide-read-path.test.ts`
already proves the server performs no guide work for a logo; that is a different claim.

### 12.2a Review finding: the deadline released the same job twice

**Confirmed and repaired.** `createLogoSlots` kept the released flag in the *caller's* closure: the
deadline called the scheduler's internal `release(next)` and then `next.giveUp()`, which in
`ChannelLogo` was `abandon` → `settle` → that returned lease. The internal release never marked the
lease released, so the identical job decremented `running` twice. The reproduction with `limit = 4`
and twelve pending jobs, replaying the exact component sequence:

| Step | Before the repair | After the repair |
| --- | --- | --- |
| Initial admitted / unsettled | 4 / 4 | 4 / 4 |
| After one expiry + component cleanup | 4 admitted, running under-counted | 4 admitted, running 4 |
| After two expiries | running under-counted further | running 4 |
| After all twelve expire and drain | running count negative | running 0 |
| Fresh batch of 16 on the same pool | **all 16 admitted immediately** | **exactly 4 admitted** |

The repair gives each job one lifecycle state (`queued` / `running` / `done`) shared by completion,
the deadline and cancellation, so capacity is returned exactly once regardless of which fires first
and regardless of what the caller does afterwards. Queued cancellation removes the job from the
queue and never decrements the running count. A late load, late error or effect cleanup after expiry
is a no-op — it cannot free a slot that has already been returned, nor admit an eighth logo.

**Measured in the real app**, same dataset, same proxy holding logo responses, `limit = 4`:

| | `f9ca30f` | This candidate |
| --- | --- | --- |
| Logo connections at first page | 4, rising to **6** after the first 15 s deadline | 4, and **4** after every deadline |
| DOM logo images while four responses are held | 8 | 4 |
| Peak connections across six navigation cycles | 6 | 4 |

### 12.2b Review finding: admission was not tied to the source, and nothing cancelled

Two further defects were reproduced through the rendered component and the real request path:

1. **`shown` was not tied to the source that earned it.** On an already shown tile a new `logoKey`
   produced a new `src`, and React rendered the replacement image in the same commit that scheduled
   the passive effect which would reset the boolean. The admission is now recorded *with the address
   it was granted for*, so a tile renders an image only when `admitted.src === src`. Measured with
   warm originals and every replacement held: exactly **4** replacement requests, **0** stale
   originals rendered, 50 usable monograms.
2. **DOM removal does not cancel the request.** Measured directly in Chromium against a server that
   never responds: `img.remove()` left the connection **open** (in-flight unchanged), and
   `removeAttribute('src')` aborted it. Since the scheduler returned capacity at the deadline while
   the request kept its connection, timed-out work accumulated *outside* the intended bound — the
   6-connection reading above is that defect, not only the double release. `ChannelLogo` now clears
   `src` on its own node when the source is abandoned, replaced or expired, and `FadeImage` forwards
   a ref so the node is reachable after React detaches it. Measured after the change, with four
   real pending responses: unmount aborts **4 of 4**, and in-flight returns to 0.

The deadline still frees the slot *before* `giveUp` runs, and `giveUp` now also cancels the request,
so a stuck provider costs one connection per logo slot and no more.

### 12.2c Review finding: a rendered component could reuse a cancelled acquisition

**Confirmed and repaired.** Binding admission to the *address* was not enough. `admitted` kept
`{src: A, shown: true}` while B waited, so returning to A satisfied the URL comparison even though
the original A acquisition had been cancelled. The rendered component — not the scheduler — was
therefore able to start a fifth request with the pool full.

Reproduced with the actual `ChannelLogo` and `FadeImage` components against the real four-slot
scheduler, React 19.3.1 and jsdom 27, with no scheduler calls and no load or error events: mount the
target with A, mount four other logos (three start, one queues), change the target to B (A is
cancelled, the fourth starts, B queues), then change it back to A. The pre-repair build rendered
**five** unfinished `<img>` elements with `src` attributes despite the four-slot limit.

| Step | Before the repair | After the repair |
| --- | --- | --- |
| Target A + four others | 4 images, A plus three | 4 images, A plus three |
| Target → B, nothing completed | 4 images, A cancelled, fourth admitted, B queued | identical |
| Target → A, nothing completed | **5 images, A's queued acquisition rendered anyway** | 4 images, A is a monogram |
| One other logo completes | 4 — A had already started | 4 — A is admitted on its own lease and only now renders |

The repair makes the grant an acquisition, not an address: `ChannelLogo` derives an identity from
the enabled state and the address, and drops a grant that belongs to a different identity **during
render** (the documented "adjust state while rendering" reset), so React re-renders before commit
and no image is ever created for a stale grant. Each acquisition also takes a monotonically
increasing token, remembered by its lease, its rendered node and its callbacks, so a late load,
error or cleanup from an obsolete acquisition can neither release the newer lease nor clear the
newer node. The four-slot cap, the fifteen-second deadline and the repaired scheduler lifecycle are
unchanged.

`tests/channel-logo.test.ts` renders the real components in jsdom and asserts the exact
A → queued B → A sequence, same-URL disable/re-enable, ordinary replacement, obsolete load/error,
the deadline, and unmount with pending responses. Run against `ff77544`'s component, the two
admission-reuse cases fail (five rendered images, and the same-URL re-enable rendering before
admission); the remaining four pass there too, and are kept as guards that the repair did not
disturb replacement, obsolete-callback, deadline or unmount behaviour.

### 12.3 The Details control: a verification error, plus one real defect

The reported "`[role=dialog]` did not appear" was **not** a product defect. The control
`US: News 0 FHD details` is the station button; activating it opens a native `<dialog>` via
`showModal()`. That element has the implicit ARIA role `dialog` and carries no `role` attribute, so
a `[role=dialog]` CSS selector can never match it. Verified on the real rendered UI:

- `dialog[open]` = 1; `[role=dialog]` = 0; accessibility snapshot reports `dialog "US: News 0 FHD"`.
- Activating it with the keyboard (focus + Enter, the remote-equivalent path) opened the dialog with
  the correct programme context, remained on `#live`, and issued **no** playback session request.
- The correct locator is `dialog[open]`, or the role form `role/dialog`.

One genuine defect was found and fixed: closing Details left focus on `<body>`. After the `Modal`
change, Back/close returns focus to the exact station control (`aria-label="US: News 0 FHD details"`).
Details also stays usable while logos are pending (4 unresolved, dialog opens and closes normally).

Note for the device run: a programme that is **airing now** opens playback, by design
(`onClick={()=>airing?watch(c):setSelection(...)}`). Only upcoming/earlier slots open Details, which
is why the control described in the report was the station button. This is existing behaviour, not a
change.

### 12.5 Remaining limits

- Not verified on the AFTMM. The browser evidence cannot substitute for it, and the 15,875 ms
  outlier was measured on the device.
- The 4-connection cap is a deliberate trade: a 50-row page shows monograms first and fills in
  progressively. Against a provider whose logos answer in ~0.9 s, the visible fill takes roughly
  10–12 s for the page while rows and navigation are immediate. If that fill feels too slow on the
  device, the number is one argument in `createLogoSlots`.
- **The fifteen-second deadline starts at admission, not at render.** A logo that waits in the
  queue is not on the clock while it waits: its timer begins when a slot is granted, so queue
  waiting time and total page fill are separate quantities. A full 50-row page therefore takes
  roughly (queue wait) + (up to 15 s per admitted request), not 15 s in total; the deadline bounds
  one admitted acquisition, not the page.
- The proxy holds logo responses; it does not reproduce provider DNS, TLS or redirect behaviour, nor
  the device's own network conditions. It also cannot reproduce a provider that streams a logo
  slowly: it holds the response, which is the harsher case for connection occupancy.
- Browser evidence here is Chromium on the development machine. `apps/web/src/compat.ts` documents
  Chromium ~66 on the API 28 Android TV image; the physical AFTMM's actual WebView version must come
  from its own runtime output, and this record does not claim to have measured it.
- The 15-second deadline is longer than the ~10–12 s a full page takes to fill. A provider slower
  than that will show monograms for the last logos until their tiles remount; that is the documented
  fallback, not a regression.
- `tests/channel-logo.test.ts` runs React 19.3.1 and jsdom 27, not the device WebView. It proves
  which component is permitted to render an image and that obsolete callbacks cannot release a
  newer lease; it does not prove browser connection behaviour, which only the Chromium probe and the
  AFTMM run can. jsdom also fires no image requests, so the test counts rendered `<img>` elements
  rather than network activity.
- No Android source changed, so no APK rebuild.
