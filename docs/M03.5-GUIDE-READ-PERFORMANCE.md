# M03.5 — Guide and logo read-path stalls: diagnosis and repair

Status: **review gate.** Branch `fix/m03.5-guide-read-performance`, stacked on
`fix/m03.4-xtream-epg`. No deployment, no merge, no shared-instance change.

The shared instance (`D:/Local/tkbox-test`, port 3000, revision `1d2c3c7`) was not started,
stopped, restarted, migrated, reset or reconfigured. Every measurement below ran on an isolated
checkout, a fresh temporary `DATA_DIR`, a separate loopback port and a synthetic dataset published
through the application's own sealed publication path.

## 1. Confirmed cost — the original diagnosis was partly wrong

The report attributed the 54 s page to repeated guide decryption. **Guide decryption was not the
cost.** Counting real vault operations during one 50-row page at `1d2c3c7` showed:

| Operation | Count per 50-row page | Verdict |
| --- | --- | --- |
| Guide blob decryption (`iptv:guide:*`) | 1 | already request-scoped, as M03.4 claimed |
| Guide JSON parse | 1 | same |
| **`iptv_sources` metadata read** | **192** | **dominant** |
| Per-channel metadata decryption + parse | ~8,400 (feeds and stacks pass) | second cost |
| Programme array scans (`guideWindow`) | 50 (one per row) | third cost |

### 1.1 The dominant defect: `IS NOT NULL` walks the whole guide blob

`IptvStore.source()` projected `encrypted_guide IS NOT NULL AS has_guide`. SQLite evaluates
`IS NOT NULL` on a stored value by reading it: on the real 37,611,340-byte guide that means walking
the entire overflow-page chain. Measured on the reproduction dataset, per call:

| Projection | ms/call |
| --- | --- |
| `SELECT id` | 0.010 |
| `SELECT id,name,revision` | 0.009 |
| `+ encrypted_endpoint` | 0.012 |
| `+ encrypted_snapshot IS NOT NULL` | 0.975 |
| **`+ encrypted_guide IS NOT NULL`** | **20.844** |
| `+ length(encrypted_guide)` | 59.932 |
| **`+ typeof(encrypted_guide)`** | **0.010** |

The guide page calls `source()` once per feed through `feedFor()` → `guideSource()` → `source()`.
At 8,436 feeds that is hundreds of full-blob walks per page — which is why the page took seconds
while `/health` (no guide read) stayed at 3 ms. The fix is `typeof(encrypted_guide)='text'`, which
reads only the value's header. Same semantics, 20.8 ms → 0.01 ms.

This is the measurement that explains the reported 54,428 ms page. Everything else below is real
but secondary.

### 1.2 Duplicate programme data

`sourceData()` parsed the sealed **catalogue** for an Xtream source to obtain channel metadata.
That catalogue carries its own full copy of the guide, so every cold read parsed the programme
collection twice: once from `xtream_accounts.encrypted_catalogue`, once from
`iptv_sources.encrypted_guide`. The published snapshot (`iptv_sources.encrypted_snapshot`) is the
small authoritative channel list and is now the only source of channel metadata.

### 1.3 Per-channel metadata, decrypting once per channel per request

Channel metadata is sealed per row. `provider()` decrypted and parsed it on every call, and a
lineup pass calls it once per channel. It is now cached by its own sealed payload: a replaced feed
is a new key, so the cache cannot serve stale metadata, and it needs no invalidation bookkeeping.

### 1.4 Per-row full-guide scans

`guideWindow()` filtered and sorted the entire programme collection for every displayed row: 50
rows × 62,660 programmes. Programmes are now grouped by guide id once per guide snapshot, and a
window is one binary search plus the programmes actually on screen.

### 1.5 Station index rebuilt on every miss

`usableGuideId()` fell back to `guideStations(xml.channels)` whenever an indexed lookup returned
`undefined`. With a complete index a missing id is a legitimate miss, so the fallback rebuilt the
station map for every channel whose id was absent — turning the common missing-id case into
quadratic work. The fallback now applies only when no index was supplied.

### 1.6 Minute boundary

`automaticStackKeys()` keyed its cache on `JSON.stringify([..., now, mappings])`, so the whole
mapping resolution and guide regrouping repeated at every clock minute. Only the schedule
comparison depends on the clock: the resolved candidates and their programmes are immutable for a
revision. The minute now re-joins cached evidence; a revision or mapping change invalidates it.

## 2. What changed

| Area | Change |
| --- | --- |
| `persistence/iptv-store.ts` | `source()` uses `typeof(...)='text'` for the three payload flags, so metadata reads never walk a blob. |
| `persistence/iptv-store.ts` | Bounded, revision-keyed cache of decrypted source snapshots and guides (`DATA_CACHE_BYTES`, 96 MiB). Entries are evicted per source when a new revision supersedes them, then by byte budget. |
| `persistence/iptv-store.ts` | Xtream channel metadata comes from the published snapshot, not the EPG-bearing catalogue. |
| `persistence/iptv-store.ts` | Per-channel metadata cache keyed by the sealed payload itself. |
| `persistence/iptv-store.ts` | `guidePage()` builds one programme index per guide snapshot and slices it per row. |
| `persistence/iptv-store.ts` | `logo()` reads a derived icon row; it no longer resolves mappings or touches the guide. |
| `persistence/iptv-store.ts` | `coverage()` also publishes each channel's guide icon in the same pass. |
| `persistence/iptv-store.ts` | `automaticStackKeys()` splits immutable resolver evidence from the minute-dependent join, and passes the guide index once. |
| `providers/iptv.ts` | `guideIndex()` also indexes guide icons; `programmeIndex()` + `indexedWindow()` replace per-row scans; indexed misses no longer rebuild station maps. |
| `services/schedule-stacks.ts` | `Candidate` exported for the store's cache type. |
| `persistence/database.ts` | Migration 1005: `iptv_channel_icons`. Existing databases are backfilled by the existing startup `relistAll()`. |
| `iptv-api.ts` | The logo route gets its own rate limit (1,200/min, matching the media routes). |

Unchanged: authorisation on every request including cache hits, SSRF/redirect/size/TLS rules for
image fetch, CSRF and origin handling, playlist-logo-then-guide-icon ordering, pagination,
ordering, filters, favourites and custom channels, and the global 120/min limiter.

## 3. Measured results

Reproduction: 8,436 feeds, 62,660 programmes with realistic descriptions, repeated quality
variants sharing a station, genuinely ambiguous guide ids, missing guide ids and missing logos, and
a second provider for scoping. Published with `publishXtream` through the encrypted vault; measured
against the **compiled** server (`npm run build`, `dist/apps/server/src/index.js`).

Both columns are the **compiled** server, the same harness, the same dataset, an isolated
`DATA_DIR` and a separate loopback port. The baseline is a detached worktree at `1d2c3c7`.

| Measurement (n = 12 unless stated) | At `1d2c3c7` | After |
| --- | --- | --- |
| Guide page, 50 rows | **p50 50,788 ms, p95 82,603 ms** | p50 185 ms, p95 241 ms |
| Guide page, 60 rows | p50 50,276 ms, p95 59,645 ms | p50 175 ms, p95 229 ms |
| Cold page (first request, compiled process) | 52,844 ms | 667 ms |
| Page after a minute boundary | — | 538 ms (also asserted deterministically in `tests/guide-read-path.test.ts`) |
| Sequential paging, 6 pages | **p50 62,588 ms, p95 74,830 ms, max 74,830 ms** | p50 245 ms, p95 446 ms |
| One logo request | p50 24,605 ms, p95 44,389 ms | p50 146 ms, p95 1,623 ms |
| Logo burst, 50–60 requests | p50 46,104 ms | p50 153 ms (warm p50 93 ms) |
| `/health` during a logo burst (n = 26) | 19 ms p50 (sampled n = 2) | p50 2 ms, p95 33 ms, max 44 ms |
| `/api/v1/me` during a logo burst (n = 26) | 2 ms p50 (sampled n = 2) | p50 2 ms, p95 87 ms, max 152 ms |
| Server RSS after the full run | **1,048 MB** | 518 MB |

The baseline reproduces the field report rather than approximating it: sequential paging measured
**54,458 ms** in one run and **74,830 ms** in another, against the reported **54,428 ms**. The
baseline logo figure (24.6 s) is worse than the reported 0.88 s because the synthetic guide is
larger than that instance's; the shape of the defect is identical.

### 3.1 Operation counts, before and after (same dataset, same store API)

Counted by wrapping `Vault.open` and `JSON.parse`; `MB` is the total JSON text parsed.

| Operation | Before | After |
| --- | --- | --- |
| 50-row page | 16,938 opens, 16,939 parses, **113.3 MB**, 49.6 s | **0 opens**, 1 parse (small metadata), 167 ms |
| 60-row page | 16,948 opens, **113.3 MB**, 52.8 s | 0 opens, 191 ms |
| 60 logo requests | 8,796 opens, **6,646 MB parsed**, 46.7 s | **0 opens, 0 parses**, 121 ms |
| Warm feed/station pass | 16,874 opens, **57.9 MB**, 46.1 s | **0 opens**, 57 ms |
| Publish/relist | 16,874 opens, 3.4 s | 0 opens, 948 ms |

The 6.6 GB figure is the clearest statement of the defect: sixty logo requests parsed the
62,660-programme guide sixty times over. After the change a logo request parses nothing at all,
because the icon is a published row.

### 3.2 Deterministic work-count assertions

`tests/guide-read-path.test.ts` asserts these directly by wrapping `Vault.open` and `JSON.parse`:

| Assertion | Result |
| --- | --- |

## 4. Reproduction dataset and how to repeat it

`scripts/bench-guide.ts` seeds a fresh temporary `DATA_DIR` (never `./data`) with 8,436 feeds and
62,660 programmes and publishes it through `publishXtream`, so storage and encryption are the real
ones. It then launches the compiled server (`dist/apps/server/src/index.js`) on a free loopback port
with its own vault key, authenticates with a session row in the shape the Xtream sign-in issues, and
measures guide pages, sequential paging, logo bursts, `/health` and `/api/v1/me`.

```
npm run build && npx tsx scripts/bench-guide.ts
```

The dataset deliberately includes repeated quality variants sharing a station, genuinely ambiguous
guide ids (`amb.*` naming two unrelated stations), channels with no guide id, channels with no
logo, and a second provider so cross-scope reads are exercised.

Machine: WSL2 on Linux 5.15, x64, Node 24.16.0, dataset and server on the same local volume.

### 3.3 Against the milestone's acceptance budgets

| Budget | Target | Measured |
| --- | --- | --- |
| Warm guide page | p95 ≤ 2 s | **p95 241 ms** |
| Cold guide page | < 5 s | **667 ms** |
| `/health` under guide/logo workload | p95 ≤ 250 ms | **p95 33 ms** (max 44 ms) |
| `/api/v1/me` under guide/logo workload | p95 ≤ 250 ms | **p95 87 ms** (max 152 ms) |
| Frontend aborts | none at 30 s | worst observed page 1.7 s (logo burst) |
| Memory across repeated pages and refreshes | no unbounded growth | 518 MB after the full run; per-source revision eviction asserted in tests |

Single-logo p95 of 1,623 ms is above a second and is reported rather than hidden: the first logo in
a burst pays for the library index and the external fetch. It is a bounded, cached cost and does
not delay guide paging (`logo burst under probes` p50 770 ms while `/health` and `/me` stay under
250 ms). The 0.88–0.90 s per-logo figure reported from the field is external-fetch time against a
real provider, which this environment cannot reproduce.

## 6. Migration and rollout

Migration 1005 creates `iptv_channel_icons` and adds no column to an existing table. A database
published before it keeps working: the first startup runs `relistAll()`, which republishes each
channel's icon from the guide already stored. **No reimport and no data deletion is required.**
Rollback is the previous commit; the new table is then simply unused and older code ignores it.

## 7. Remaining acceptance

No browser or physical AFTMM run was performed here. The remaining step is unchanged from M03.4's
handover: deploy the branch head to an isolated instance, then on the AFTMM open Live TV, let the
logos settle, page forward several times and open a programme's details. The fix is only accepted
when paging stays responsive with logos loading and programme titles, descriptions and time windows
are correct.

No Android source changed, so no APK rebuild is required.

## 8. One deliberate limit change

The logo route had no limit of its own, so a guide page's 50–60 logo requests drew on the shared
120/min ceiling. On a real device that means ordinary browsing can exhaust the budget that `/health`,
`/api/v1/me` and every other route share, and a benchmark burst produced `429 RATE_LIMITED` on
`/health`. The logo route now carries its own 1,200/min ceiling, exactly as the live-segment and HLS
routes already do for the same reason. **The global limiter is unchanged at 120/min**, every
credential and state-changing route keeps its tighter limit, and authorisation still runs for every
logo request.

## 9. Hermes deployment and physical retest

Deployment remains a Hermes task. The shared instance at `http://192.168.0.30:3000` must not be
repointed at a different `DATA_DIR`, restarted in place, migrated or reconfigured as part of this
change's verification.

1. Check out `fix/m03.5-guide-read-performance` in an isolated directory, separate from the shared
   checkout, and run `npm ci && npm run typecheck && npm test && npm run build`. Expect **255/255**
   tests and a clean build.
2. Start it on a port other than 3000 with a **copy** of the environment, and either a synthetic
   `DATA_DIR` or a consistent copy taken with SQLite itself (`.backup` or `VACUUM INTO`), never a
   plain file copy of a live database that has a WAL. If a copy is used, copy `secret.key` with it
   and keep it out of the checkout.
3. Migration 1005 runs on the first startup and creates `iptv_channel_icons`. Confirm:
   `SELECT COUNT(*) FROM iptv_channel_icons` is 0 before the startup pass and non-zero after it.
   No reimport, no guide deletion and no key regeneration is required.
4. Confirm the read path is healthy before any device test:
   - `GET /health` returns `{"status":"ok"}`.
   - `GET /api/v1/guide?start=…&end=…&offset=0&limit=50` returns real titles and descriptions.
   - `GET /api/v1/iptv/channels/<id>/logo` returns an image, and the server logs no guide read for
     it.
5. **Rollback**: stop the new process and start the previous revision. The new table is then unused
   and older code ignores it; no data was migrated or deleted. There is no schema change to revert.
   Do not roll back by restoring a backup — that would discard later sessions.
6. On the AFTMM: sign in normally (no seeded cookie), open Live TV, let the logos settle, page
   forward several times and open a programme's details. Report:
   - whether paging aborts at all (it must not reach the 30 s deadline);
   - approximate time for the first page and for each subsequent page;
   - whether logos appear, and which channels still show a monogram;
   - whether titles, subtitles, descriptions and time windows are correct;
   - whether `/health` stays responsive while scrolling and during the logo burst.
7. No APK rebuild: no Android source changed.

## 10. Remaining unknowns

- The single-logo p95 of 1,623 ms here is dominated by the first external fetch in a burst and the
  logo-library index load, both bounded and cached. Real-provider fetch latency (the reported
  0.88–0.90 s) cannot be reproduced without that provider, so the physical run is what confirms it.
- The synthetic guide is representative in size and shape, not in provider-specific quirks: it does
  not reproduce the exact 8,385-channel/69,733-programme feed M03.4 imported. The counts and the
  shape of the defect are what carry over.
- The data cache budget (96 MiB of sealed payload) is sized for two full guides plus their channel
  snapshots. A deployment with many large providers at once will evict and re-read rather than grow
  without bound; that is the intended trade-off, not a measured limit.
