# Fork structure and upstream synchronisation

Fork: `tacticdemonic/tk.box` · Upstream: `Enkiduke/tk.box` · Default branch: `main`

## Remotes

```sh
git remote -v
# origin    https://github.com/tacticdemonic/tk.box.git   (fork: push here)
# upstream  https://github.com/Enkiduke/tk.box.git        (read-only reference)
```

Never force-push, never push to `upstream`, and never rewrite `main`. Upstream is the
source of truth for the original Plex, Live TV, custom channel and EPG behaviour.

## Branch model

| Branch | Purpose | Rules |
| --- | --- | --- |
| `main` | mirror of upstream plus fork-only automation | fast-forward to `upstream/main`; no feature work; only sync PRs and workflow fixes land here |
| `develop` | integration branch for fork features | feature branches merge here after review and green CI |
| `feature/*` | one milestone or capability | branch from `develop`; rebase on `develop`; open a PR to `develop` |
| `fix/*` | bug fixes that should return upstream | branch from `main` when the fix is upstreamable, otherwise from `develop` |
| `sync/upstream-*` | generated by the sync workflow | disposable; carries one merge of `upstream/main` |
| `release/apk-*` | stable Android/Fire TV release lines | cut from `develop` when the APK milestone lands; tags `apk-vX.Y.Z` |

Current development branch: **`feature/xtream-firetv`** (branched from `develop`, which is
level with `main` at M01).

Rules of thumb:

- A change that could be offered upstream (a bug fix in existing behaviour) starts from
  `main` and is kept small.
- Fork database migrations use the `1000+` range (`1001`, `1002`, …); upstream owns
  `1..999`. Never edit an existing migration: add the next fork number. This keeps both
  migration streams additive when upstream merges.
- Fork-only work (Xtream adapter, Android shell, release automation) stays on `develop`
  and feature branches, so upstream merges rarely conflict.
- Fork-specific documentation and workflows are separate files rather than edits to
  upstream files such as `README.md`, precisely to keep merges clean.

## Daily upstream check

`.github/workflows/upstream-sync.yml` runs at **05:17 UTC every day** and on
`workflow_dispatch`:

1. checks out fork `main` with full history;
2. fetches `upstream/main` and counts commits behind/ahead;
3. if behind, creates `sync/upstream-YYYYMMDD-HHMMSS` and merges `upstream/main`;
4. installs dependencies and runs `typecheck`, `test` and `build` on the merged tree;
5. pushes the branch (never `main`) and opens a **pull request to `main`**, marked draft
   when verification failed;
6. on merge conflicts, aborts the merge and opens (or comments on) an issue listing the
   conflicting files. No PR is created.

The workflow never merges, never force-pushes and never touches `upstream`.

### Reviewing a sync PR

- Read the upstream commit list in the PR body.
- Confirm the CI workflow is green on the PR (the sync job's own run is a second signal).
- Pay attention to files this fork owns: `apps/server/src/providers/xtream.ts`,
  `apps/server/src/persistence/xtream-store.ts`, `apps/server/src/xtream-api.ts`,
  `apps/server/src/services/xtream-service.ts`, `tests/xtream.test.ts`, `docs/`, and
  `.github/workflows/`.
- Merge intentionally with a merge commit (keeps upstream history), then fast-forward
  `develop` from `main`:

```sh
git checkout main && git pull --ff-only
git checkout develop && git merge --ff-only main
git push origin develop
```

### Manual check

```sh
gh workflow run upstream-sync.yml --ref main
gh run watch
```

Locally, without Actions:

```sh
git fetch upstream
git log --oneline main..upstream/main
git checkout -b sync/upstream-manual main
git merge --no-edit upstream/main
npm ci && npm run typecheck && npm test && npm run build
git push origin HEAD
gh pr create --base main --head sync/upstream-manual --fill
```

## Scheduling prerequisite

GitHub runs scheduled workflows only from the **default branch**. The workflow files are
therefore on `main` as a two-file automation-only commit (`f192ed8`, PR #2) and nothing
else; all feature work stays on `develop` and `feature/*`. Both workflows are registered as
active, which also confirms the YAML parses.

`workflow_dispatch` remains available for an immediate check:

```sh
gh workflow run upstream-sync.yml --ref main
gh run watch
```

M01 verified the workflow's git logic (behind detection, merge branch, push, conflict
reporting and merge abort) with a local two-repository simulation. Hosted-runner execution
could not be observed: every dispatched run stayed queued with no runner assigned, an
external GitHub Actions capacity condition rather than a workflow error. The first real run
should be checked with `gh run list` once runners are available.

## Releases (Android/Fire TV)

1. Cut `release/apk-1.x` from `develop` when the APK milestone is accepted.
2. Bump `versionCode` monotonically; `versionName` follows `1.x.y`.
3. Build the signed APK in CI, attach it to a GitHub Release, publish a `latest.json`
   update manifest.
4. Tag `apk-v1.x.y`. Stable tags are immutable; fixes go to a new patch release.
5. `main` continues to track upstream independently of APK releases.

## Permissions and protection

Recommended repository settings (owner action):

- Protect `main`: require a pull request, require the `CI` check, disallow force pushes
  and deletions.
- Protect `develop` similarly, allowing the maintainer to merge feature PRs.
- Keep Actions enabled with `Read and write permissions` (the sync workflow needs
  `contents: write`, `pull-requests: write`, `issues: write`; they are declared per
  workflow, so the repository default can stay read-only).
- Do not grant the workflow permission to merge: merge is intentionally manual.

If a permission prevents the workflow from pushing or opening a PR, it fails visibly in
the Actions log; run the manual commands above with a maintainer token instead.
