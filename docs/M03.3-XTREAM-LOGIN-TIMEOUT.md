# M03.3 — Xtream sign-in timeout: deployment handover

Status: **review gate.** No deployment has been performed by OMP. The shared Windows test
instance (`D:/Local/tkbox-m032`) was left stopped and was not touched; all work here used an
isolated in-memory database, a synthetic provider and separate ports.

## What was wrong

`POST /api/v1/auth/xtream/login` authenticated against the provider and then ran the complete
catalogue + EPG import inline before setting the session cookie. With 8,436 channels the request
took 78.5 s server-side while the web client aborts at 30 s, so sign-in from the Fire TV UI could
never succeed. The M03.2 origin fix was correct and is unchanged.

## What changed (server-delivered only)

| Area | Change |
| --- | --- |
| `POST /auth/xtream/login` | One bounded provider call (account authentication), then identity + session + provider row, then queue an import. Returns `{status, accountId, role, account, import, importError?}` without waiting for the catalogue. |
| `XtreamImports` (`apps/server/src/services/xtream-imports.ts`) | Managed lifecycle for sign-in, manual and scheduled imports: one active job per provider (partial unique index), two server-wide, abort on shutdown, stale rows marked `interrupted` at startup. |
| `POST /xtream/accounts/:id/refresh` and the admin equivalent | `202 Accepted` with the job; no longer holds the request. |
| `POST /admin/iptv/sources/:id/refresh` for an Xtream source | `202 Accepted` with the provider import; M3U/XMLTV keep their existing synchronous contract. |
| `GET /xtream/accounts/:id/imports` | `{imports, active, latest}`; the same check as the account itself, so a foreign account gets `404`. |
| Migration 1003 | `xtream_imports` table plus a partial unique index for one active job per provider. |
| Publish path | Per-pass guide index, reused channel rows and lean source reads. The 8,436-channel publish dropped from 38 s to ~1.1 s of event-loop time. |
| Web client | `apps/web/src/import-progress.ts`, `import-banner.tsx`: bounded 3-second polling, honest states, Retry, imports shown in the guide instead of "No channels". `api()` names a deadline abort as a timeout. |

Not changed: CSRF/origin checks, cookie attributes, bootstrap-token rules, Plex sign-in, provider
access grants, HTTP-provider opt-in, the 30-second client deadline, playback, the Android app.

## Deployment steps for Hermes

The instance is stopped. Use the reviewed head of `fix/m03.3-xtream-login-timeout` with the
existing protected configuration and state. The backend code revision is
`55c7b8afa79829421525295d89f3a902e17db98b`; later commits on the branch are documentation only, so
either that commit or the branch head runs the same server. Do **not** regenerate the encryption
key or point `DATA_DIR` somewhere new.

1. Stop any running process for the test instance. Never copy `tk.box.sqlite` while it is open.
2. Take a consistent backup of the whole state directory (`tk.box.sqlite` plus `-wal`/`-shm`) and
   keep `SECRET_KEY_FILE` separately.
3. Check out the reviewed commit into `D:/Local/tkbox-m032` (or a new directory), then:
   `npm ci`, `npm run typecheck`, `npm run build`.
4. Start with the existing environment (`D:/Local/tkbox-test/tk.box.env`): `APP_HOST=0.0.0.0`,
   `APP_PORT=3000`, `APP_ORIGIN=http://192.168.0.30:3000`, absolute `DATA_DIR`/`SECRET_KEY_FILE`,
   `FFMPEG_PATH`/`FFPROBE_PATH`. Do not change these values for this fix.
5. Migration 1003 applies on the first start, adding `xtream_imports` and its index. It creates a
   new table only and does not touch catalogue, session or provider rows. Rollback is: stop, restore
   the backup, start the previous commit; the dropped table is the only loss.
6. Confirm `GET /health` returns 200 and `GET /api/v1/setup` shows the expected bootstrap state.
7. Sign in normally from a browser at `http://192.168.0.30:3000`. Expect the form to close in about
   a second and "Signed in. Loading channels…" while the import runs. Do **not** seed a cookie.
   Status: `GET /api/v1/xtream/accounts` then
   `GET /api/v1/xtream/accounts/<id>/imports` should show the job move `queued`/`running` →
   `completed`, and the guide fill in.
8. Check the log for `xtream import did not complete` with a stable code if the provider is slow
   or unavailable; the sign-in itself still stands and the account keeps its last known channels.

## Risks

- **Provider variability.** The synthetic panel is faithful to the documented API, not to a real
  subscription. A panel that is slow to *authenticate* (not merely to list) will still fail the
  sign-in, correctly, with `XTREAM_TIMEOUT` after the server's 30 s fetch bound.
- **Single-process assumption.** The import manager and the existing source scheduler assume one
  backend process owning the SQLite state. Two processes would each run their own queue; the
  database unique index still prevents duplicate active rows, but the capacity limit is per
  process.
- **First import duration.** A genuine 8,436-channel catalogue still takes as long as the provider
  needs; the difference is that the viewer is now inside the application and can watch cached
  channels while it runs.
- **Guide-only failures** are reported on the job (`guideError`) and in the UI, not as a failed
  sign-in. A provider with no XMLTV feed will show that state until a guide is configured.
