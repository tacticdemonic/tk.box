## 1. Confirmed cause of the missing guide

Not provider unreachability. The provider answered **HTTP 200 in 522 ms** with a valid gzip XMLTV
feed; the application rejected it twice, at two different stages.

| Stage | Observed | Verdict |
| --- | --- | --- |
| Provider response | `200`, `content-encoding: gzip`, 2,875,083 compressed bytes | healthy |
| Fetch validation | `content-length` matched the body; complete | pass |
| Decompression | inflated to **21,601,581 bytes (20.6 MiB)** | **failed: 16 MiB cap** |
| XML parse (once the cap was raised) | `<!DOCTYPE tv SYSTEM "xmltv.dtd">` prologue present | **failed: unconditional DTD rejection** |
| Channel mapping | 2,501 of 8,436 channels declare an `epg_channel_id`; 1,850 resolve to a usable guide id | healthy, with real provider ambiguity |
| Persistence | guide stored and published | healthy |

Four independent defects, all application-side:

0. **`parseXmltv` rejected 173 guide ids that the provider shares between different stations and,
   more damagingly, discarded the listings of every id it declared more than once.** The feed
   declares `bbc1.uk` four times — `BBC One | SD |`, `| FHD |`, `| HD |`, `| Catchup Backup`. The old
   rule required an id to appear exactly once, so the programmes for the most-watched stations were
   quarantined even after the feed parsed.
1. **`source-fetch.ts` / `iptv.ts` shared one 16 MiB ceiling** for transferred and decompressed
   bytes. `gunzipSync` threw `ERR_BUFFER_TOO_LARGE`; that is not an `AppError`, so
   `RestrictedSourceFetcher` wrapped it as `SOURCE_FETCH_FAILED`, and `transportFailure()` mapped
   that to the catch-all `XTREAM_UNREACHABLE`. That single code is what the UI rendered.
2. **`parseXmltv` refused every `<!DOCTYPE`**, including the conventional XMLTV external-DTD
   prologue. This would have kept the guide empty even after the size fix.

Evidence that the failure was at transport and not later: `iptv_sources.encrypted_guide` was NULL
while `encrypted_snapshot` held the 8,436-channel catalogue, and every completed import carried
`guide_error=XTREAM_UNREACHABLE`. A parser rejection would have recorded `INVALID_XMLTV` or
`EMPTY_XMLTV`; only the transport catch-all produces `XTREAM_UNREACHABLE`.

## 2. What changed

| Area | Change |
| --- | --- |
| `providers/source-fetch.ts` | Per-call `SourceLimits` (transferred and decompressed, both still bounded). The Xtream guide path raises them explicitly to 16 MiB compressed / 64 MiB inflated; every other caller keeps the 16 MiB default. |
| `providers/source-fetch.ts` | Structured `SourceFetchError` codes with safe numeric detail (`httpStatus`, `bytes`, `limit`, `elapsedMs`, `compression`, `network`): HTTP status, size, decompression limit, unsupported encoding, invalid gzip, invalid UTF-8, incomplete response, DNS, TLS, network, timeout, redirect policy. |
| `providers/iptv.ts` | `parseXmltv(input, {maxBytes, maxProgrammes})`. A programme-count breach throws instead of being counted as a quarantined record. The standard external-DTD prologue (`<!DOCTYPE tv SYSTEM "xmltv.dtd">`) is accepted; an internal subset or any entity declaration is still refused. |
| `providers/iptv.ts` | `guideStations()` replaces the "exactly one declaration" rule. An id is usable when every declaration of it names one station (`stackKey`, which already ignores resolution/backup qualifiers; additionally `Catchup`), and ambiguous when different stations share it. Used by parsing, automatic mapping, candidates and manual approval, so one rule governs all four. |
| `providers/xtream.ts` | `transportFailure()` maps each fetch code to its own `XTREAM_*` code. Only an unknown failure remains `XTREAM_UNREACHABLE`. |
| `providers/xtream.ts` | Short-EPG fallback requests by **`channel.streamId`** and stores listings under **`channel.tvgId`**. The old code sent `tvgId` as `stream_id`; on the real panel that returns zero rows. |
| `providers/xtream.ts` | Timestamps: validated Unix seconds (`start_timestamp`/`stop_timestamp`, numeric strings), XMLTV `+HHMM`, ISO 8601 with offset, and wall-clock strings only with the provider's own timezone. Host local time is never used. Ordering, range and overlap are validated; rejects are counted. |
| `providers/xtream.ts` | `decodeGuideText`: base64 only when the string round-trips exactly and decodes as fatal UTF-8. Plain titles are left intact. Output bounded. |
| `providers/xtream.ts` | Fallback budget: ≤40 channels, 4 concurrent, 20 s wall clock, abort-aware, stops on the first rate-limit/HTTP/timeout refusal. Reports `requested`/`succeeded`/`skipped`/`mappedChannels`. |
| `providers/xtream.ts` | `GuideStatus` distinguishes `available`, `partial`, `unmatched`, `empty`, `failed`, `disabled`, plus the retained `primary` diagnostic. |
| Migration 1004 | `xtream_imports.guide_status`, `iptv_sources.guide_status`. Column-presence checked, because migration 1002 rebuilds `iptv_sources`. |
| `persistence/iptv-store.ts` | A guide-only failure keeps the previously published guide and records `XTREAM_GUIDE_RETAINED`. Fixed: `publishXtream` read a `has_guide` alias that `SELECT *` never produced, so a retained guide was silently dropped. |
| `web/src/import-progress.ts`, `live.tsx` | Messages describe what the viewer has: complete, partial (with coverage), unmatched, empty, retained, or failed with a reason code and HTTP status. |

Unchanged: sign-in path and 30 s client deadline, playback, CSRF/origin rules, Plex, M3U, Android
media redirect protections, the SSRF address policy, TLS verification.

## 4. Authorised real-provider observations

Read-only and bounded: one XMLTV read, one stream listing, and short-EPG calls for a handful of
channels. No mass scan, no playback interruption, no credential logged.

| Observation | Value |
| --- | --- |
| XMLTV response | `200`, gzip, 2,875,083 bytes, 522 ms |
| XMLTV inflated | 21,601,581 bytes (20.6 MiB), 234,256 elements, depth 3 |
| XMLTV content | 8,385 channel elements (1,945 distinct ids, 179 duplicated), 69,733 programmes |
| Parser cost | 537 ms to parse 20.6 MiB (measured with saxes directly) |
| Short EPG by `stream_id` | 4 rows; fields `start_timestamp`, `stop_timestamp`, base64 `title`, plain `description` |
| Short EPG by `epg_channel_id` | 0 rows — the old fallback's request shape |
| Server timezone | `Europe/London` |

After the fix, the real feed through the real server code produced `guide: available` with 62,553
programmes. Of the 2,501 channels that declare an `epg_channel_id`, **1,850 resolve to a usable guide
id and 956 have programmes in the current window**; the rest have listings outside it. The
rendered `/api/v1/guide` payload now carries real listings — `BBC One | FHD |` shows "Shift the
Thrift" and "Escape to the Country" where it previously showed "No guide data".

Guide-page latency on the real 8,436-channel lineup is ~1.1–1.4 s of server work for 60 rows,
dominated by the pre-existing station-stacking pass; the same fixture measured 0.9–1.0 s before
this change and 6.1–7.9 s end-to-end on both branches, so no regression is introduced. An earlier
draft added the new JSON column to `source()`, the per-channel projection; it was moved to a
targeted read after measurement showed it in the hot path.

Remaining ambiguity is genuine and left alone: `bbc2.uk` is declared both as `BBC Two` and as
`BBC Two NI`, so no listing can be attributed automatically. Those channels honestly show no guide
data, and an administrator can map them explicitly.

## 7. Hermes handover

Deployment is a separate task. Do **not** merge PR #8; deploy the branch head explicitly.

1. Stop or leave the shared instance alone — this change does not require stopping it. Deploy to
   an isolated checkout and a separate port, or schedule a window; do not point it at the shared
   `DATA_DIR`.
2. `npm ci && npm run typecheck && npm test && npm run build` on the target checkout.
3. Start with the existing environment. Migration 1004 adds one nullable column to
   `xtream_imports` and one to `iptv_sources`; it inspects column presence, so it is safe if
   migration 1002 rebuilt `iptv_sources`. Rollback: stop, restore the pre-deploy backup, start the
   previous commit. The new columns are the only loss and neither is read by older code.
4. Trigger one refresh (`POST /api/v1/xtream/accounts/<id>/refresh` with `{"includeEpg": true}`) and
   poll `GET /api/v1/xtream/accounts/<id>/imports`. Expect `state: completed` and
   `guide.source: "xmltv"`, `guide.state: "available"`, `guide.parsedPrograms` in the tens of
   thousands.
5. If instead you see `guide.primary.code`:
   - `XTREAM_HTTP_STATUS` / `XTREAM_RATE_LIMITED` — the provider refused; `httpStatus` is included.
     Do not treat this as a broken deployment.
   - `XTREAM_RESPONSE_TOO_LARGE` — the feed grew beyond 64 MiB inflated; `limit` is included.
   - `XTREAM_DNS_FAILED` / `XTREAM_TLS_FAILED` / `XTREAM_NETWORK_FAILED` — the host genuinely could
     not be contacted.
   - `XTREAM_GUIDE_RETAINED` — this refresh failed but earlier listings are still being served.
6. Physical guide retest on the AFTMM: sign in normally (no seeded cookie), open Live TV, and
   confirm listings on the channel rows rather than "No guide data". Report which channels still
   show no data, and their names; expected gaps are the genuinely shared provider ids
   (`bbc2.uk` = BBC Two + BBC Two NI) and channels whose only listings are outside the window.
   Confirm playback and Back still behave as accepted.
7. No APK rebuild. Report back: the `guide` object from step 4, any `XTREAM_*` code with its
   `httpStatus`/`limit`, and the physical result.

## 8. Remaining unknowns

- Whether the provider's guide remains complete as it grows. The ceiling is now explicit
  (64 MiB inflated) rather than silently at 16 MiB; a feed beyond it reports
  `XTREAM_RESPONSE_TOO_LARGE` with the limit, which is actionable.
- The guide ids the provider genuinely shares between different stations (87 in this feed).
  Attributing their listings would be a guess; those channels honestly show no guide data and an
  administrator can map them explicitly with the existing review screen.
- Channels whose only listings fall outside the displayed window still read as "No guide data" for
  that window. That is a window answer, not a missing guide.
